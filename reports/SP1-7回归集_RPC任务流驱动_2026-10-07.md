## 1. 背景与范围

上一交付（7d79a19）给验收运行器建好了 `TaskFlow` 端口，但仅进程内 FakeLLM 实现；验收方案步骤 3（真实 Key 全量回归）与步骤 4（进程级 kill/恢复）缺少真实执行载体。本次交付 `RpcTaskFlow`：经 JSON-RPC 驱动 `python -m engine` 真实进程，使运行器能以同一套代码执行生产级断点恢复演练与真实 Key 回归。

## 3. 设计决策

1. **协议面零扩展**：仅使用既有 RPC 方法（initialize/task_create/start_stage/answer_gate/get_status），不改契约——无需 CT-V2 登记与 ARCH 评审。
2. **引擎 home 本地只读访问**：阶段定位读 `engine_home/checkpoints.db`（与 `StageOrchestrator.restore` 同口径），usage/产物哈希读 `engine_home/audit.db`。理由：RPC 响应不携带阶段数据（受理即回），改契约加数据回传需走评审且收益低；回归驱动本就管理引擎 home 的生命周期，本地只读属工具自治范围。已在模块 docstring 声明。
3. **失败归因重映射**：阶段 failed 时引擎经 `get_status.last_error` 暴露 `"TypeName: detail"`，驱动按类型重映射（Connection/Http/Network/Adapter→adapter；Timeout/Sandbox→sandbox；其余→orchestrator），保证运行器四分类归因在 RPC 通道同样成立。
4. **阻塞传输 + `asyncio.to_thread`**：独立进程串行驱动是回归工具语义；不阻塞运行器事件循环，产品客户端不使用本实现（客户端走主进程 EngineHost）。

## 4. 暴露并修复的缺陷（1 处）

**生产进程留痕从不记录模型调用**：管线各阶段 data 均不含 `model` 字段，而 `__main__._build_sink` 仅在 `model and usage` 同时存在时记录 model_call——真实引擎进程的 audit_trail 中 model_call 恒为空（SP1-6 用量留痕开环）。进程内测试因自建 sink 无条件记录而未暴露；RPC 系统测试以留痕为地面真值，首次实跑即命中。修复：四阶段 data 透传 `model`（tool_loop 内循环多调用场景按 `unknown` 登记），生产 sink 恢复设计语义。

## 5. 量化验收

- 引擎全套：**180 passed / 1 skipped / 覆盖率 93.52%**（≥80 门禁；rpc_flow.py 由系统测试覆盖）。
- 系统测试（真实 `python -m engine` 进程）：
  - 全程驱动：四阶段 + 门禁 → 论文落盘于引擎 home、留痕恰 4 次 model_call、产物哈希 64 位；
  - 进程级 kill/恢复：modeling 后硬杀进程 → 重建引擎进程（同 home）→ 自检查点续跑完成 → audit.db 全程恰 4 次 model_call（无重放地面真值）+ 检查点四阶段留档。
- 脚本实跑（`--driver rpc --per-category 1`）：4/4 通过、4 题进程级恢复演练全过、决策门 BASELINE_ONLY（护栏语义正确）。
- ruff / mypy 全绿。

## 6. 11-05~11-14 真实 Key 回归用法（窗口任务已就绪）

```bash
python scripts/run_regression.py --driver rpc \
    --api-key sk-xxx --base-url https://api.deepseek.com/v1 \
    --model deepseek-chat --provider deepseek        # 全量 20 题 + 每类 kill/恢复演练
```

- 结果以 `CHANNEL_REAL` 登记，报告按通道分离，`decision()` 出 Go/No-Go 建议（正式判定会 11-14，QA 主持）；
- 沙箱双模式：`--sandbox docker` 经 `ERDOS_SANDBOX_REQUIRE_DOCKER=1` 强制引擎 Docker 模式（DEC-006 fail-closed）；
- 失败样本不删除：归因（重试 ≤3 次策略属 QA 执行层，运行器保持单次语义）。
