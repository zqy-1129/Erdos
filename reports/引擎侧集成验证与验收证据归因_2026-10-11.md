## 4. 过程记录：自己的用例抓出自己的缺陷

`test_pipeline_stage_level_fallback_unchanged` 在我改完第一轮后变红。它原本断言"`mode` 键不存在＝没走循环"，我改成"`execute_count == 0`＝Registry 没被执行"，于是暴露出：**降级路径现在经 Registry 分发（W23②），执行的是 Registry 里的沙箱，而 `isolation_mode` 我当时读的是 `self._sandbox`**。

- 生产装配下 `__main__.py:305-308` 把同一个沙箱对象既给 pipeline 又给 registry，所以产品不会出错；
- 但"因为装配巧合所以字段为真"正是本项目反复拒绝的形状（DEC-006 要求如实上报隔离模式，G32/G41 家族都是"两处各写一遍"）；
- 修法：由**执行体自报**——`code_tools` 把 `isolation_mode` 写进 `ToolResult.data`（它手里就是真正跑代码的 sandbox），工具循环经 `SolveState.isolation_mode` 带出（`LOOP_CHANNELS` 从 `SolveState.__annotations__` 导出，加一个字段即成，两套后端共用同一声明）；pipeline 两条分支都只读带出来的值，读不到就记 `unknown`。
- 现在的断言同时测两件事：`data["isolation_mode"] == "counter"`（取自 Registry 里那个替身沙箱，而不是管线手里的 `SubprocessSandbox`）+ `inner.execute_count == 1`。

**另一条自纠**：跑测试计数时我给命令又加了一次 `-q`，而 `pyproject.toml` 的 addopts 已带 `-q` → `-qq` 把末尾"N passed"整行吞掉，看起来像输出被截。改用一键门的汇总行取数（该坑已在本机环境记忆里，本轮又踩，说明"命令带不带 -q"要当默认习惯改掉）。

## 8. 同日追加二：内核评审 + 进程级演练把上一批（`27a7367`）的修复证伪（本轮提交 `a479ff5`）

补上 §7 登记的那条 ⚠️（进程级信号演练）之后，**它当场把上一批的退出链修复证伪**：信号送达、退出码 0，stderr 全空——点名记录从未写出。根因是结构性的，不是时序巧合：

- 上一批把取消接在 `serve()` **返回之后**的那句 `drain(cancel=...)` 上；
- 而生产形态下宿主保持 stdin 管道打开，`serve()` 正阻塞在读行，**300ms 的 GRACE 窗口内它不会返回** → `os._exit(0)` 先发生 → 取消、点名、CancelledError 分支一条都不执行；
- Ctrl+C 之所以看起来正常，是因为 KeyboardInterrupt 从 `run_until_complete` 里**抛出来**，走的是另一条文路。**只测能走通的那条文路，就会把"不可达的修复"当成已交付。**

改法：`_graceful` 里就经 `loop.call_soon_threadsafe(...)` 排 `runtime.drain(cancel=True)`（handler 在主线程执行、循环可能正卡在 selector 上），`serve()` 之后那句保留作兜底；配合 §7 的"点名先于 gather 落盘"，取消记录才真的能落 stderr。

**本轮同时对自研内核（636 行）与图节点体做了评审**，逐条留证据：

| 检查点 | 结论 |
|---|---|
| `_loop` 的异常面 | 只捕 `Interrupt`，其余上抛 ✓；`Interrupt` 是 Exception 子类，但 `orchestrator/*.py` 内**零处** `except Exception` 包在 suspend 外 → 挂起不会被吞（registry 的宽 except 在另一条调用栈上，门禁不经过它） |
| 通道语义 | `apply` 对未声明键 fail-loud、`apply(None)` 容忍（与 langgraph"无更新"同形）；`values()` 返回副本 ✓；`ThreadStore` 一图一实例、随编排器 GC，无累积泄漏 |
| 门禁破坏性分支 | `answer_gate` 入口校验 `decision ∈ {pass, reject}` → "非 pass 即丢本阶段产物"不可由畸形入参触发 ✓ |
| F-007 红线 | `delete_stage` 只删 `checkpoints` 表；**全引擎唯一的 DELETE 就在这里**，audit_trail 未被触碰 ✓ |
| G43 | 复核 `start_stage`：else 分支无条件建 `StageOrchestrator` → 骨架支经 RPC 仍不可达 → **仍是裁决项，没有误当缺陷顺手改掉** |

两条 latent 观察**只登记不动**（都触及跨实现口径，不是工时）：① 内核没有 superstep 上限，而 langgraph 有 `recursion_limit=25`——选一个既兜住接线错误又不打死 `solve_loop` 预算（8 次派发 × 回边）的值需要实测；② resume 值未被消费时内核静默继续，改成报错就是与 langgraph 的有意偏离，须追认。

守护与反证：新增 `test_signal_stop_names_the_interrupted_stage_in_a_real_process`（真发信号 + `stage.progress<1.0` 作在跑同步点）与正向对照 `test_no_signal_means_no_cancellation_record`（EOF 档不得出现点名）；**摘掉 handler 排程后两者变红**（已实测，随后恢复），3 次连跑稳定。AST 守护改为盯"handler 自己排取消 + 经 call_soon_threadsafe"。

## 11. 同日追加四：判定通道评审查出「一份论文两个哈希」（提交 `769e1ce`）

`_check_writing` 过去只验 `paper_sha256` 的格式与产物文件的存在，从不比对两者；实测（Windows）它们本来就不一致：`write_text` 默认把 `\n` 译成 `\r\n`，于是阶段记录按字符串字节取哈希、留痕 `artifact_index` 与合规声明按文件字节取哈希。审计一比对就像"产物被改过"。修三件：LF 写入、哈希取落盘字节、硬检查补「声明==实际」。三个测试夹具因照抄生产写法而从未暴露它，一并校正——**夹具与生产同源是"验证"成立的前提**。

撤回一处改动并记下理由（免得后人再走一遍）：`_check_solving` 改成「mode 不认识就判违规」实测后放弃——默认分支要求 `exit_code==0` 且有输出/产物，本就 fail-closed；换文案收益≈0，代价是 W23② 之前的 stage_level 检查点恢复时会被误判、白跑一次求解。改用正向用例钉住"默认分支不放过空数据"。

另一处自纠：我第一版把不变量写成"产物不得含 CRLF"，真机跑完发现论文里就有子进程 stdout 带回的 CRLF（属数据，不是翻译）——正确要求是"落盘字节 == 内存字符串字节"。**凭直觉写不变量，就会被真数据打回重写**，这条按本项目惯例记下来。

## 17. 追加（2026-10-12）：CI 成为第二条验证通道，以及两条"只有 CI 能抓"的缺陷

本机解释器被组织策略拦下之后（§15），经用户批准把验证通道换到 CI。这不是退而求其次——
它当场抓出两条本地永远看不到的缺陷，也暴露了守护与 workflow 各自的一个隐含假设。

**三仓 CI 在 `c883bee` 上全绿**（用仓库公开 API 读，本机无 gh）：

| workflow | 结果 | 说明 |
|---|---|---|
| `engine-ci`（ubuntu-24.04） | ✅ | 八步逐项通过：Install → Ruff → **Mypy** → 依赖边界守护 → **Pytest（覆盖率 ≥85%）**。这是这批引擎改动**第一次在 Linux 上跑全量测试** |
| `server-ci` | ✅ | 含 `SP2-8 PG 压测（P95 < 200ms）` |
| `client-ci` | ✅ | 矩阵 ubuntu-24.04 与 windows-2022 两个 job 都过 |

**红→绿一：`win_job.py` 的平台可见性（提交 `3092bf1`）**
`engine/sandbox/win_job.py:104/119/134/141: error: Module has no attribute "get_last_error"`。
根因：typeshed 把 `ctypes.get_last_error` 声明在 `sys.platform == "win32"` 之下——**本地 Windows 的
mypy 看得见，CI 的 Linux 看不见**；而调用点的平台条件藏在 `_kernel32()` 的返回值里（运行时
`getattr(ctypes, "WinDLL", None)`），mypy 推不出"到这行必然是 Windows"。**运行时不受影响**（Linux 走不到那几行），
但整条 engine 门被堵死 = 流水线阻断。修法沿用同一文件里已经用对的模式（`WinDLL` 那处），新增
`_last_error()` 用 `getattr` 取，**取不到返回 None 而不是 0**（补 0 会被读成"没错"）。
全仓 `ctypes.*` 直连复扫：只剩跨平台的那几个，两个 Windows 专属都在 `getattr` 兜底后面。

**红→绿二：引用守护把正确的哈希判成假引用（提交 `c883bee`）**
`AssertionError: 交付报告里有指不到的提交：` 点了 8 条，其中 `14b4888`/`c3f73a7` 就是本仓引擎批次自己的提交。
它们当然存在——是 `actions/checkout@v4` 默认 **`fetch-depth: 1`**，历史对象不在本地，`git cat-file` 自然失败。
本地开发永远是全史，所以这条守护上线以来从没在"它真正要防的场景"里被测过。两边各补一刀：
workflow 显式取全史（让守护**真跑得动**），守护自己在浅历史下 `pytest.skip` 并写明原因（**正向下对照用例也一起跳**，
否则"假哈希要被抓、真哈希不能被抓"在浅克隆里失去意义）。本地用 `git cat-file -t` + `merge-base --is-ancestor`
八条全查过：八个哈希都在 develop 祖先里，确认是环境限制而非报告写错。

**判据（本轮最该留下的一条）**：本机门是 Windows、CI 门是 Linux，**两者能抓的缺陷集合不同**。
`--target all` 本地全绿不等于跨平台门通过；平台可见的类型声明、CI 才有的环境假设（浅克隆、缺依赖、
区分大小写的文件系统）只有第二条通道能暴露。

**CI 覆盖不到的，别当成已验**（写清楚免得误读这张绿表）：
- SP1-7 的四档集成（`--driver inproc/rpc/parity/bench`）不在 CI 里跑，仍是本地脚本；
- Linux 上 Windows 专属用例（Job Object 强制、`SIGBREAK` 进程级演练）不会真正执行——
  所以 `_last_error()` 在 **Windows 侧的行为本轮未复跑**（逻辑上是 `getattr` 命中即返回 int，
  但这属于"推理不是证据"，恢复解释器后要随四档锚点一起复算）；
- 真实 Key 通道与 11-05~11-14 窗口无关，决策门仍是 BASELINE_ONLY。

复算（无需本地 Python）：`https://api.github.com/repos/zqy-1129/Erdos/actions/runs?per_page=6`
与 `.../commits/<sha>/check-runs`；失败时 `.../check-runs/<job-id>/annotations` 现在带正文（§17 的两条红就是这么读到的）。
