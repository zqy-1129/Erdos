## 1. 结论先行

幂等账本 `operations.db` 的键是 `(task_id, stage, attempt, exec_seq)`——它只回答"**这是第几次派发**"，
不回答"**这次派发要跑哪段代码**"。两处因此把"没做成的事"记成"做成了"：

1. **复用不看请求内容**（D1）。恢复重跑时模型在同一个 `exec_seq` 上给出的通常是**另一段代码**，
   而引擎查到记录就跳过执行，并回注 `[系统] 复用已完成执行 #N（引用：…）`。于是：模型这次写的
   代码一次都没跑，它看到的"执行结果"来自上一个程序，而协议里没有任何一句话说出这件事。
   这正是 DEC-005"已成功副作用不重放"被实现成"同位置的副作用不重放"——前提丢了。
2. **失败也登记成 `done`**（D2）。`record_done` 在 `dispatch()` 之后无条件调用，而 `status` 列
   只有 `done` 一个写入方（`operations.py` 自己的口径就是"执行成功后登记"）。一次失败的派发进了账，
   下一次恢复就会把它复用成"已完成执行"——把失败谎报成成功，且谎报的是资金/算力之外的**事实**。

两条都是**真实 Key 通道才暴露**的缺陷：FakeLLM 逐字确定（同位置必给同一段代码），而两条回归通道
又都走 stage_level（§5），所以 637 例单测与 20/20×2 通道全绿都没有红过。这不是"测试没写到"的
运气问题，是**判据本身把"位置"当成了"身份"**。

## 2. 修法与取舍

- `engine/orchestrator/operations.py:30` 新增 `request_digest(name, arguments_json)`：
  sha256(`f"{name}\n{arguments_json}"`)。取**参数原文**而不是规范化 JSON——厂商两次给出的键序/空白
  可能不同，那样会得到不同摘要并触发重跑。**这是刻意选的坏方向**：多花一次沙箱可以承受，
  把没跑成的说成跑过了不可以。`engine/orchestrator/operations.py:53` `OperationRecord.same_request()` 是唯一的判定入口。
- 复用判据变成"同键 **且** 同请求"（`engine/orchestrator/solve_loop.py:328`）。旧库行没有摘要 → 按"无法证明是同一
  副作用"处理：重执行，并在成功后把摘要补齐，第二次恢复才回到不重放（收敛性有用例钉）。
  与既有防御"非 `done` 按未完成处理"同口径（`engine/orchestrator/operations.py:112`）。
- `record_done` 收进 `if result.ok:` 分支（`engine/orchestrator/solve_loop.py:346`）。失败不入账 ⇒ 崩溃点矩阵的
  "执行后未记=重执行"这条本来就成立，之前是被写入方破坏的。
- `force` 刷新条件从"产物损坏"扩为"**换请求 or 产物损坏**"。同键换了内容必须刷新摘要，否则下次
  恢复仍然不复用而白跑。**账本不是留痕**：force 覆盖不影响合规可见性——每次真实派发都在
  `audit.db` 的 `tool_call` 里逐条追加（W22①/W23 的"留痕条数=调用次数"），审计数的是那张表。
  这一点写在 `operations.py` 模块 docstring 末尾，因为"append-only 账本被 UPDATE"看着像违反红线。

## 3. 三条既有用例测的正是缺陷本身（已校正）

`test_restore_reuses_intact_artifact_without_replay` / `test_restore_hash_mismatch_reexecutes_and_refreshes` /
`test_restore_hash_mismatch_repair_failure_keeps_record` 三条都用一份四元素脚本队列，让"恢复后的
那次运行"在 seq=1 上给出 `print('b')`（首跑是 `print('a')`），并断言"零重放 / 因损坏重执行"。
**旧实现下这两件事不可能同时成立**：换了代码却按位置复用，则哈希篡改那条分支从未被真正走到——
第三条用例的"因损坏重执行"其实是"因换了请求而重执行"。改后三者的恢复侧一律重放同一段代码，
让每条用例只测它声称测的那件事。这是本仓反复出现的那一类：**改前的旧用例可能测的就是缺陷本身**。

## 4. 证据

- **先红**（实现前）：3 条新用例中 2 条按预期红——`assert 1 == 2`（改了代码没重跑）、
  `assert 0 == 1`（无摘要旧行被当同一请求复用）；第 3 条因我自己的 `ExecutionResult` 少传
  `stderr` 报 TypeError，不算信号（修正后红）。
- **单独反证①**（撤内容判定：`stale_request = False`）→ **精确 2 例红**
  （`test_restore_does_not_reuse_a_different_request`、`test_legacy_record_without_digest_reexecutes_then_converges`），
  其余 27 绿。
- **单独反证②**（把 `record_done` 挪出 `result.ok` 分支）→ **精确 2 例红**
  （`test_failed_dispatch_leaves_no_done_record` + AST 结构守护）。
  第一次跑这条反证时它叠在了① 上（备份取的是已退回的版本），得 3 红——**归因错了就重测**，
  单独重跑后才拿到"2 红"这个干净结果。
- **结构守护** `test_dispatch_structure_pins_the_two_reuse_preconditions`：`record_done` 必须仍在
  测试式含 `result.ok` 的分支内、`same_request` 不得被删、复用观察文本全文只有一处。
  行为用例会漏的形态（替身沙箱下失败分支根本走不到）由这条兜住。
- 迁移用例用**真 SQLite 造旧库**（无 `result_sha256`/`request_digest` 两列 + 一条旧行），
  断言打开即补齐两列、旧行摘要读回 `None` 而不是猜一个。
- 四档复跑：inproc **20/20**（4 题 kill 恢复）、rpc **20/20**（真实引擎子进程）、决策门仍
  `BASELINE_ONLY`（FakeLLM 不计判定分母，DEC-024）。

## 5. 覆盖边界（这条最重要，别把 §4 读成"端到端验过了"）

`engine/__main__.py:191` 无 Key 装配返回 `solve_llm=None` ⇒ `StagePipeline` 的前置条件
（registry **且** solve_llm **且** operations 且 `tool_mode=="tool_loop"`）不成立 ⇒ **两条 FakeLLM
回归通道结构性地跑不到求解内循环**。实测报告第一屏就是那句归因：
「求解路径 stage_level 20 · 沙箱隔离 subprocess 20」。

所以：
- §4 的 inproc/rpc 20/20 是**无回归信号**（证明我没改坏别的），**不是**本批修复的证据；
- 本批修复的证据是单测级，但其中"账本"与"分发"是真的：真实 SQLite `OperationLog`、真实
  `build_default_registry` 分发、真实 `SolveLoop`；替身只有沙箱执行体（计数/写文件）与 LLM 脚本；
- **11-05 真实 Key 窗口是这条路径第一次被端到端跑到**，而 G53 在那之前修掉了——这是本批的排期意义；
- 进程级 `tool_loop` + kill/驳回重跑的同型场景**仍无覆盖**。`engine/tests/test_rpc_flow.py:162` 已有可用的
  mock 厂商替身（`tools_mode=True` 时求解带 tools 发起，`test_real_key_channel_full_chain_with_mock_vendor`
  实测 5 次调用），补这条的载体是现成的，代价是要手工驱动"驳回→重跑"而不走 `AcceptanceRunner`；
  本批未做，登记为下一批候选，**不发 W 号**（手册发号处未见对应单，空号比补上更坏）。
