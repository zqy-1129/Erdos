## 1. 结论先行

1. **把"异常被吞"当成一类缺陷做了全仓排查**：AST 扫 `server/app/` 下所有 `except` 处理器，凡是处理器体只有 `pass/continue/break/.../return None` 的一律列出——共 **7 处**：3 处属正常控制流、1 处收窄后仍属预期结果（这 4 条进白名单并写明理由），3 处是真实缺陷或隐患（月赠、消息总线、令牌校验），已全部处置。
2. **月赠发放失败此前完全不可见**（上一批 §5 #2 登记的遗留）：`except Exception: continue`，无计数、无日志、无告警；更严重的是失败发生在共享会话里，**一次 flush 失败会把会话拖进待回滚状态，后面所有人都跟着失败**。现在每人一个保存点隔离、失败计数进批次结果、任务层转 P1 告警、明细 exec_id 落日志。
3. **挖出一颗测试顺序地雷**：`alembic` 的 `fileConfig()` 默认 `disable_existing_loggers=True`，迁移跑过之后**整个进程的 `erdos.*` 日志被禁用**。表现是 caplog 抓不到记录，且只在 `tests/test_migrations.py` 先跑的顺序下出现（pytest 收集顺序 api → test_migrations.py → unit），单独跑那几个用例永远是绿的。
4. **给这类缺陷上了机器守护**：`test_silent_exception_guard.py` 让"新增静默 except"直接红，白名单条目必须写理由、失效即红（防腐）。
5. **复核了昨天的一处收紧**：并行合入的 PR #7 给 `/v1/billing/products` 带来了客户端调用方（`client/main/cloud/commerce.ts`），但该调用在渲染层被 `session.status !== "signed-in"` 挡在登录之后 → 10-09 的"商品目录需登录"结论仍成立（取证见 §5）。
6. 状态：**已实现待验收**（P1 档位与"失败明细只留 20 条"两处口径需 ARCH 追认）。

## 3. 月赠失败的取证与口径

- **"缺积分账户"不是失败原因**：`PointsService.grant_points` 内部走 `get_or_create`，没有账户行会自动建（实测 `granted:3 failed:0`）。所以测试用 monkeypatch 让**指定用户**在发放途中抛错——被测的是"批次里炸一个人"的后果，不是积分域自己的失败分支（那些由 `test_points*.py` 覆盖）。
- **保存点隔离是可验证的**：3 个订阅中间那个失败，断言另外两人各自拿到 400 分且批次结果为 `granted:2 failed:1`。旧实现下这条断言不可能通过。
- **`already_ran` 与"零失败"必须可区分**：`MonthlyGrantRun.outcome` 在批次被占用时为 `None`，否则"这个月没跑"会被读成"跑了且没人失败"。
- **告警档位定 P1**（`monthly_grant_failure`，已登记进 `METRIC_SEVERITY`）：失败意味着已付费用户没拿到当月积分，属权益承诺破损，与容量水位类 P2 不同档。文案只带计数并指路 exec_id，用户明细走日志与流水，不落告警载荷（隐私与载荷体积两条都照顾到）。

## 4. 迁移日志地雷的定位过程

1. 全量门禁红 2 条，都是 caplog 断言；单独跑这两条用例绿；`tests/unit` 整目录跑也绿。
2. 二分：`pytest tests/test_migrations.py tests/unit/test_message_bus.py` → 红。确认是**顺序依赖**，不是并发或随机化（未装 xdist/randomly 插件）。
3. 排除 `dictConfig`/`basicConfig`/`logging.disable`/`propagate=False`（全仓 grep 零命中）后定位到 `app/migrations/env.py:21` 的 `fileConfig(config.config_file_name)`——默认参数就是 `disable_existing_loggers=True`。
4. 修法一行：`disable_existing_loggers=False`，并把"为什么"写进注释。回归守护不需要新用例：本批那两条 caplog 用例在全量顺序下就是它的守门人（此前它们正是被这颗雷炸红的）。

## 5. 对 10-09 收紧结论的复核（代码在我脚下变了）

并行会话合入 PR #7（`148a9ad` 客户端购买流）后，`/v1/billing/products` **出现了调用方**：
`client/main/cloud/commerce.ts:37` → `checkout-panel.tsx` → `pages/billing.tsx`。

复核结论：**10-09 的收紧仍然成立**，依据是渲染层的登录门——`client/renderer/src/entry.tsx` 里
`if (session.status !== "signed-in") page = <LoginPage/>`，结算页与商品拉取都在登录态内；
且 `client/main/cloud/http.ts` 在有令牌时自动附 `Authorization: Bearer`，401/403 走统一清会话回调。
所以"契约要凭证 + 实现要凭证 + 客户端只在登录后调用"三方一致。

方法论上记一条：**"查调用方"的结论有时效**。昨天 grep 到零调用方是真的，今天合并后就假了；
凡是基于"无人调用"做出的收紧，在跨端代码合入后要重查一次。
