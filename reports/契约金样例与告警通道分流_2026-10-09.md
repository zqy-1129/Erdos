## 1. 结论先行

1. **快照字节序有了跨端共同判据**。此前它是"文档里一段示例 + 两端各自手抄的断言"：服务端有**两份**独立 `_canonical`（权益快照、阶段许可），客户端还有第三份 TS 实现，而 `sp3-3` 把期望值写死在 TS 里——服务端改字节序客户端不会红，故障表现为"离线宽限全部验签失败"。现新增 `contracts/snapshot-vectors.json`（载荷→规范化字节→签名 三元组），两侧各读同一份文件断言。
2. **stdio UTF-8 + LF 从"客户端文档里的一条注意"升格为契约条款**。原先只写在 `client/main/engine-protocol.md §2`，三边零机器判据。现上移为 `contracts/engine-rpc.schema.json` 的 `transport` 段，引擎与客户端各有一条守护。
3. **告警三档分级走到了外发最后一公里**。`AlertRouter` 此前零生产调用方：分级只决定事件是不是 `warning`，看板与 Webhook 载荷里既无档位也无通道，接收端拿到的永远只有 `warning/info`，**P0 与 P2 在值班侧同形**。现在载荷带 `level` + `channel`，去重与路由合一，`_routed` 无界列表换成按通道有界计数。
4. **邮件通道仍未接入**（P1 该走邮件，需 SMTP 凭据 = DEC-021 未决）。本轮只落地"通道判定与分级可见"，**不假装已经发送**；已登记遗留项。
5. 状态：字节序与传输条款= **已实现并验证**（三仓门禁全绿）；按通道实际投递= **部分实现待验收**（飞书/消息共用一个 Webhook 端点，邮件未接入）。

## 2. 交付内容与关键取证

### 2.1 金样例把"隐含的默认值"变成显式条款

规范化字节序最容易出事的是 **Python `json.dumps` 的 `ensure_ascii` 默认值**：现网快照/许可字段全是 ASCII 时间戳与整数，任何一份实现改成 `ensure_ascii=False`（"让日志里能读中文"）都不会立刻出事，但中文字段一旦进入载荷（题面摘要、套餐名），三端就会分叉。因此：

- 契约文档 §1 从 3 条扩为 5 条，把 `ensure_ascii`、`\uXXXX` 小写、**增补平面字符转 UTF-16 代理对**（`😀` → `\ud83d\ude00`）、"只允许整数"、"null 键保留"逐条写成显式规则；
- 金样例专门放一条 `canonicalization-only` 向量覆盖非 ASCII / 代理对 / 负数 / 空串 / null / false；
- 另加一条向量断言"载荷在文件里是**乱序**书写的"——否则"键排序"这条规则实际上从未被测到；
- 签署用的是**一次性测试密钥**：私钥只在生成脚本进程内存中存在、未落盘未提交，契约文件只带公钥（SPKI DER）与签名，因此两侧既能比字节序又能真验签。

### 2.2 篡改向量与文档同源

`tamper-purchased-boost` 向量把 `purchased_balance` 从 100 改成 999999 而签名仍是原载荷的，两侧都必须判为无效；文档 §2 的示例串本身也是一条向量（`test_doc_example_matches_the_machine_vector` / 客户端同名用例直接读 `contracts/snapshot.md` 比对）。**只改文档不改契约文件会直接红**，这是本轮把"人读的口径"和"机器判的口径"钉成同一个源的做法。

### 2.3 transport 段的参数是取出来的，不是抄的

引擎侧守护断言 `configure_stdio()` 对三条管道的 `reconfigure()` 实参逐字取自契约（`encoding=utf-8`；stdin/stdout `errors=strict`、stderr `errors=replace`；stdout `newline="\n"`），并用 AST 断言 `engine/__main__.py` 的 `main()` **第一句**就是 `configure_stdio()`——晚一步，首行 Key 与首帧请求已按宿主码页读走。协议管道坚持 `strict`：坏字节按 `replace` 会变成 U+FFFD 并静默改写题面/`task_id` 后照常执行，比直接失败更危险。

客户端侧守护把条款落到行为：请求行 LF 结尾且无 CR、中文以 UTF-8 原样写出、stdout 中文事件行完整解析、单行上限**取自契约常量**而非本地硬编码、首行 Key 注入同样 LF 收尾；再加一条源码扫描——主进程不得出现 `PYTHONIOENCODING`（编码由引擎进程入口负责，不允许两端各自兜底）。

### 2.4 一个"接了线反而更瞎"的坑：去重只能问一次

`BrokerAlertOutlet` 与 `AlertRouter` 各持一份 `SilenceManager` 时，同一次 `emit` 会问两次 `should_send`：第一次写入账本、第二次立刻被**自己刚写入的记录**判为重复 → 路由返回 `None` → 整条告警静默丢弃。修法是共用同一份账本，并把通道判定合进去重分支（`triggered` 且 `dedupe` 才走去重路由，恢复通知与自带状态机的采样侧走 `channel_for` 纯映射）。

### 2.5 有界账本

`AlertRouter._routed: list[tuple[Alert, Channel]]` 在常驻进程里必然无界增长；改为 `{Channel: int}` 计数（键空间固定 3 个）。路由历史本就该由告警事件落库与看板承担，不该由内存列表承担。
