## 1. 结论先行

1. **接口面基本是干净的**：契约 10 方法 / 6 事件、方法名、事件名、参数名、transport 条款、退出码 2 路径、引擎不直连云端——这些**都对得上代码**。引擎侧的跨进程契约不需要重写。
2. **最危险的不在引擎侧文档，在客户端架构文档**：`02_客户端架构与模块设计` 的主进程↔引擎接口表写
   `{ taskId, execId, stage, modelCfg, keys }`——**把 API Key 放进 RPC 参数**，与 DEC-011（Key 只经 stdin 一次）
   和契约 `additionalProperties:false`（只有 `task_id`/`stage`）同时冲突。照它实现即破红线。P0，待 W35 出更正增量。
3. **《数据模型设计》描述的持久化模型在三个实现里都不存在**：`stage_runs`/`checkpoint_data`/`tasks` 在服务端
   ORM（24 表）、客户端迁移、引擎本地库里全部查无；而引擎两个文件的注释自称"与《数据模型设计》对齐"。
   这不是"文档落后"，是**语义单源缺位**——恢复定位、留痕可删性这些行为判据没有权威定义。P0，待 W38。
4. **同一文档内部自相矛盾两处**：①`04` 第 21 行"留痕表硬性追加、禁止删除"vs 第 270 行"客户端留痕跟随任务生命周期，任务删除可手动清理"；②`PRD §9.2` 覆盖率 `>70%` vs `engine/pyproject.toml:67` 实际生效门禁 `85`。P0/P1。
5. **判据执行者用的是最旧的那份文档**：`15_QA工程师手册` v1.0 至今未更新，仍写"SP1-7 用 10 道真题"（实为 20）、
   "覆盖率 >70%"（实为 85），且通篇没有 DEC-024"FakeLLM 不计入 ≥85% 分母"。11-14 判定门若照它执行，
   **必然产出假绿灯**。P1，最高优先级修复项。
6. **本批自己写的东西也被同一套标准查出来了 3 处**（不回避）：技术设计引用的 `test_orchestrator_surface.py`
   与 `native_backend.py` 注释引用的 `test_orchestrator_backend.py` **当时都不存在**；§7.2 承诺的"autouse fixture
   让 27 个测试文件双实现各跑一遍（300→600）"**从未实现**。已补文件 / 改注释 / 在 §13 登记第 7、8 条偏离。
7. **顺带查出并修掉一个 P0 数据正确性缺陷（存量，非本批引入）**：恢复定位把"未识别的检查点状态"当作
   "门禁已通过"直接推进下一阶段，而客户端对同一未知值判定相反。详见 §4.1。

**本单真正的风险面在写向，不在读向**：宿主读到 >1MiB 的行会**整行丢弃**并记协议错误（`client/main/engine-host/rpc.ts:99`），所以引擎发出超长的后果不是报错，而是"事件/响应静默消失"。因此写向的保证是**绝不发出超限行**：

- 事件：就地截断最长的**内容**字段（`gate.failed.reason`、`tool.call.args_summary`、`model.delta`）并打 `truncated: true`；`task_id`/`stage`/`seq`/`trace_id` 这类**路由字段绝不截**——截断会把事件投给错的任务或让宿主无法按 seq 去重；
- 极端（必填路由字段本身撑爆）：**放弃这一条并计数**，因为发出去宿主必丢，等于既丢事件又坏链路；被放弃的事件也不进回放缓冲，否则 `events_replay` 会补发一条从未成立的事件；
- 响应：超限降级为 JSON-RPC 错误信封，消息里给出路（"调小 `events_replay` 的 limit 分页取"）。最现实的触发点就是 `events_replay` 一次取 200 条事件；
- 计数经 `get_status.protocol` 暴露给宿主（`{oversized_in, oversized_out, truncated_events}`），不是烂在引擎内存里。`get_status.result` 无 `additionalProperties:false`，故属**加性变化、零契约 diff**。

**一处刻意保留的边界**（写进契约 `enforcement_status`，不含糊）：读向上限管的是"引擎愿意解析并分派的单行规模"，**不是 stdin 缓冲字节数**。stdin 是 `configure_stdio()` 重配过的 UTF-8 strict 文本层、且首行握手从同一层读，改走 `sys.stdin.buffer` 做有界读会有双层缓冲丢字节的风险，收益不抵代价。

**两个自己踩出来的坑（比结论更值得记）**：

1. 截断循环第一版**死循环**——"砍一半 + 追加标记"在字段长度已接近标记长度时不再变短，循环原地打转。修法是"进不了就清空"，并留一条专门用例（`test_truncation_terminates_when_field_is_near_the_mark`）钉这个边界。
2. 第一版用例用真实 1MiB 字符串跑每一条断言，把整个套件拖到**分钟级**（跑到超时被后台杀进程）。现在行为用例把 `MAX_LINE_BYTES` monkeypatch 到 4KiB——同一份代码路径、不牺牲判定强度——另留一条真实数值的用例（`test_real_limit_rejects_oversized_request`）。

### 8.16 内核与退出链评审：进程级演练把上一批的修复证伪（提交 `a479ff5`）

### 8.19 恢复定位的判据：写入时间序不是业务序（提交 `618f781`，2026-10-11）

`StageOrchestrator.restore()` 用 `completed_stages(...)[-1]` 决定"恢复到哪个阶段"，而
`completed_stages` 是 `ORDER BY updated_at` —— **最近写过哪一行**，不是**业务上走到哪一段**。
两序今天在可达数据上恰好同值（每阶段各写一次、按业务序推进），所以这不是现网缺陷，而是
**把巧合当不变量**的一条判据：任何重跑/回退更早阶段的通道（manual_edit 回退、旁路修库、老库迁移）
都会让恢复点退回早阶段，把已完成的建模/求解进度吃掉。

构造"先落 `modeling(done)`，再回写 `analysis(stage_done)`"即复现：旧实现答 `analysis`（门禁未决、
重挂），按阶段序取最靠后者答 `solving`（已过门禁 → 推进）。两条用例入
`engine/tests/test_checkpoint_resume.py` 并做过反证（退回 `completed[-1]` 后双双变红，随后恢复）。

同批 `operations.py` 的两条评审结论：

- `records()` 的 `ORDER BY exec_seq` 缺 `attempt`——跨尝试会把两次运行的 exec_seq 交错成一条假时间线，
  修为 `attempt, exec_seq`。它同时是**零生产调用方**（只有测试按条数断言），属"有 API 没接线"一族；
  留/删属口径 → 本批只把排序改对并如实登记，不擅自删。
- `status` 的注释写着"running 为过程态"，实际写入方只有 `done` 一个；按事实更正——
  "非 done 一律按未完成处理"是**防御**，不是现网分支（fail-closed 的检查保留）。

**一处我自己写错的理由被撤回**（它同时进了 docstring 和该提交说明）："`updated_at` 若退化成字母序，
writing 会排在 solving 前面"——**不成立**：`STAGES` 本身就是字母序（analysis<modeling<solving<writing），

### 8.21 写向行宽评审：守护只兜了成功响应，五条错误出口全裸（提交 `2b4ce09`，2026-10-12）

继续评审未读模块（`ipc/server.py` / `ipc/rpc.py` / `ipc/limits.py`）。W36 把 NDJSON 单行上限落成了
"读向拒绝 + 写向降级"，契约 `transport.limits.enforcement_status` 也照此写了"引擎读写双向……超限行按
协议错误拒绝/降级"。**实况只有半边**：`handle_line` 的成功响应过 `_bounded`，五条 `encode_error` 出口
直接返回，一条都没兜。

危害不是"错误消息难看"。宿主对超限行的处置是**整行丢弃并记协议错误**（`client/main/engine-host/rpc.ts:99`），
所以一条长错误响应的对外表现是**这条请求永远没有回应**——比报错误更坏。实测（不是推演）：

| 触发面 | 实测数字（修前） |
|---|---|
| 非 Scalar `id` 被回显 | 请求行 1,048,570 字节（**读向放行**）→ 错误信封 1,048,590 字节，**越上限** |
| 计数器可见性 | 越限的那次 `get_status.protocol` 仍是 `{'oversized_in': 0, 'oversized_out': 0, 'truncated_events': 0}`——降级发生过而账上看不见 |
| 任意异常文本 | 兜底分支 `内部错误：{exc}` 的长度不由引擎决定（`{exc}` 可以是厂商/库的长文本） |

修两层，顺序是有意的：

1. **读侧堵住放大通道**：`parse_request` 按 JSON-RPC 2.0 校验 `id` 只能是 String/Number/Null，
   对象/数组/布尔一律 `INVALID_REQUEST`。回显调用方给的非 Scalar id 本身就是"读向放行的行能让写向
   产出一行超限"的来源。客户端实测用自增数字（`rpc.ts:61 const id = this.seq++`）→ 收紧零影响。
2. **写侧每条出口都过降级**：新增 `_bounded_error()`——超限时**先砍消息保住 `id`**（宿主靠 `id` 把失败
   对上号），连"空消息的信封"都回显不起 `id` 才退到 `id=null`。截断按 **UTF-8 字节**预算（`clip_bytes`）：
   按字符数截会得到"看着没到上限、编码后超限"的行（CJK 每字 3 字节），而协议量的是字节。
   计数只在"决定降级"那一层加，一条出站行只计一次（`_degraded_error` 不计数）。

**跨端口径要说的两件事**（都只登记，不擅自动客户端）：

- 降级到 `id=null` 时，宿主 `dispatch()` 的响应分支是 `typeof line.id === "number"`（`rpc.ts:130`），
  null id 会被**静默忽略**——那条请求等到自己的超时。可见性因此回到引擎侧的 `oversized_out` 计数。
  要补的是 FE 侧一个"未配对响应"计数，或让引擎在降级时另发一条可路由的事件（后者属契约面）。⚠️ 未做。
- 契约文字这次**不需要改**：`enforcement_status` 的"双向"承诺本来就写着，是本实现没兑现到位——
  这是"契约与实况不符"里"实况欠账"的那一类，修法是实现追上契约，不是把契约降回实况。

守护与反证：`engine/tests/test_error_line_bound.py` 24 例（三条降级路径 + 正向对照"短错误逐字不动不计数"

只许出现在兜底层"）。三次反证各自变红后恢复：错误出口退回不兜 → 4 例红；一条出口绕过助手 → 2 例红；

### 8.22 证据渲染评审：零样本被印成 0.00%，"无失败"成了最坏的一种空断言（提交 `371c574` + `16cbb4a`，2026-10-12）
