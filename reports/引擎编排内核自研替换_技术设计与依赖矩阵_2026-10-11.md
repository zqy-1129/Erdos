## 1. 结论先行

1. **LangGraph 的使用面很窄，但承担的语义很重。** 全引擎只有 2 个文件 4 处 import（`graph.py:19-21`、`solve_loop.py:27`），用到的 API 只有 6 个符号（`StateGraph`/`START`/`END`/`interrupt`/`Command`/`InMemorySaver`）；但它提供 11 条运行时语义（§3），其中 3 条一旦复刻不准就是数据正确性问题而非崩溃——**S5/S6 interrupt-重放** 、**S7-S8 END 后从 START 重入** 、**I4 双层检查点的分工**。
2. **替换的净收益是实测的，不是推测的**（§2.2）：冷启动里 **约 90% 是框架 import**（LangGraph import 实测 p50 858ms，引擎冷启动 p50 953.5ms / p95 969.0ms，12 样本）；传递依赖闭包 **46 个包**、lang* 系列 **637 个 .py 文件**，直接决定 SP5-3 PyInstaller 产物体积与启动时间；`langgraph==1.2.12` 与引擎版本绑定发布的升级风险随之消失。
3. **发现一条现存合规暴露，且替换后按构造消失（P0 级，与重构同批处置）**：宿主环境变量 `LANGCHAIN_TRACING_V2=true` 会让引擎把**题面原文 POST 到 smith.langchain.com**。已真机实证（§2.3，`MARKER_LEAKED: True`）。触发条件是 env 被设成字符串 `true`（`1`/`TRUE`/`True` 均不触发），客户端 `client/main/engine-host/host.ts:191` 用 `env: {...process.env}` 原样继承 → 命中面是"用户机/开发机恰好装过 LangSmith 工具链"。这条与「题面不出本机」（DEC-010）、「平台不中转」、遥测隐私红线**三重冲突**。缓解（env 剥离）与根治（摘除依赖）都在本方案内，且**缓解不等价于根治**——46 包闭包里还有别的 env 驱动行为。
4. **切法是"新增内核 + 开关切换 + 三级双轨"，不是一次性替换。** 8 个阶段（P0~P7），每阶段一个 commit、一个可独立回滚点；过渡期 `ERDOS_ORCH_IMPL=langgraph|native|shadow` 三值开关，默认 `langgraph`（行为零变化），最后一步才翻默认值并摘除依赖。任一阶段出问题：**未翻默认值前**改环境变量即可（不用发版），**已翻**则 `git revert` 单提交。
5. **双轨校验不做生产逐请求镜像**，这是有意的偏离并写明理由（§6.4）：BYOK 下镜像等于**花用户两份 token + 跑两遍沙箱**，违反预算红线与 DEC-024 口径。替代方案是三级：单测级 parity 矩阵（每 PR 门）+ 回归级双轨（FakeLLM 20 题通道，批次门）+ 灰度级双路对照（按装机分组，比结果不比逐请求）。
6. **质量标准是可判定的，不是形容词**（§7）：现有 297 个测试函数 27 个文件**全部保留**，只允许改断言中的框架自省字段（3 条，见 §7.2）；覆盖率阈值不低于 90.66%；`contracts/` 零 diff；冷启动 p95 不劣化且目标 ≤500ms；契约 10 方法 + 6 事件 + `get_status` 快照 + `checkpoints` 表字节级兼容（**老任务库必须能被新引擎恢复**，见 §4.5）。

## 2. 现状梳理

### 2.1 范围判定：为什么"原有框架"= LangGraph，而 pydantic/httpx 不动

判据顺序用仓库自己的用词，不靠猜：

| 证据 | 位置 | 结论 |
|---|---|---|
| 「**编排框架**顶层包」 | `engine/tests/test_dependency_boundary.py:17`、`server/tests/unit/test_arch_boundary.py:20` | 仓库把 langchain/langgraph 归类为"框架"，把 pydantic/httpx 归为库 |
| CI 门禁只拦 langchain/langgraph | `.github/workflows/server-ci.yml:28-31`、`client-ci.yml:27-30` | "框架"的机器定义就是这两个 |
| 引擎生产代码三方 import 实测 | AST 扫描 `engine/**`（排除 tests）：`langgraph` 4 处、`pydantic` 5 处、`httpx` 2 处、`yaml` 1 处 | LangGraph 是唯一被"自研实现"可替代的运行时框架 |
| pydantic 是**直接**使用不是传递 | `tools/base.py:15`、`code_tools.py:7`、`plot_tools.py:11`、`registry.py:15`、`search_tools.py:7`（实测 5 处，tests 除外） | 摘 langgraph 时 pydantic 必须**转为直接声明**（现在被注释写成"LangGraph 传递依赖"，`pyproject.toml:17-18`） |

`httpx` 承的是 BYOK 直连厂商（`adapters/openai_compat.py`），换成 stdlib `urllib` 属于把网络 I/O 层重写，风险与本重构正交，**本批不动**（若日后要"零三方依赖引擎"，那是另一个 DEC 与另一份设计）。

### 2.2 框架成本实测（重构前基线，全部本机可复算）

| 指标 | 实测值 | 复算命令 |
|---|---|---|
| LangGraph 6 符号 import（新进程） | 5 样本 851.9/854.7/858.3/858.6/863.4 ms，**p50 ≈ 858ms** | `./.venv/Scripts/python.exe -c "import time;t=time.perf_counter();from langgraph.graph import END,START,StateGraph;from langgraph.checkpoint.memory import InMemorySaver;from langgraph.types import Command,interrupt;print('%.1f ms'%((time.perf_counter()-t)*1000))"` |
| 其余保留依赖 import | pydantic+httpx+yaml = **170.2 ms** | 同上换 import |
| 引擎冷启动（spawn→initialize 响应） | **p50 953.5ms / p95 969.0ms**（12 样本，FakeLLM 通道） | `./.venv/Scripts/python.exe scripts/bench_engine.py --samples 12 --out docs/acceptance/before` |
| 传递依赖闭包 | **46 个包** | 见 §11 附脚本 |
| lang* 已安装 .py 文件数 | **637**（langsmith 306 / langchain-core 182 / langgraph 78 / langgraph-sdk 45 / langgraph-checkpoint 17 / prebuilt 7 / protocol 2） | 见 §11 附脚本 |
| 沙箱超时强杀精度 | 2.39s @ timeout 2.0s（目标 ≤4s）通过 | `scripts/bench_engine.py` |
| 四阶段墙钟（FakeLLM） | analysis 0 / modeling 0 / solving 406 / writing 15 ms | `scripts/bench_engine.py` |

**关键推论**：冷启动 953.5ms 里 858ms 是框架 import → 框架占 **≈90%**。摘除后理论下界是"解释器启动 + 自有 import"，即 p50 约 300~400ms。这把 `initialize` 的 p95 余量从 2.06 倍（969 vs 2000）扩到 4~6 倍，并给 SP3-7「冷启动 <3s」的客户端总目标腾出实际预算。

### 2.3 隐式依赖里最要紧的一条：env 驱动的题面外泄（实证）

**探针**（`docs/acceptance/probe_tracing.py`，gitignore 证据件，复算命令见 §11）：本地起 HTTP 假端点冒充 LangSmith，fresh-env 子进程跑真实 `StageOrchestrator` 四阶段，题面里埋唯一标记。

```
LANGCHAIN_TRACING_V2=true LANGCHAIN_API_KEY=lsv2-fake LANGSMITH_ENDPOINT=http://127.0.0.1:<port>/api \
  ./.venv/Scripts/python.exe docs/acceptance/probe_tracing.py <port>
→ tracing_is_enabled: True
→ REQUESTS: 3        # GET /api/info + POST /api/runs/multipart
→ MARKER_LEAKED: True   # 题面原文出现在外发请求体
```

| 三态 | 口径 |
|---|---|
| 实测 | 上述三行输出；env 值为 `true` 时启用，为 `1`/`TRUE`/`True` 时 `tracing_is_enabled()=False`（判据 `== "true"`，`langsmith/utils.py::tracing_is_enabled`） |
| 实测 | 客户端不做 env 过滤：`client/main/engine-host/host.ts:191` `env: {...process.env, ...modelEnvironment, ERDOS_ENGINE_HOME: home}`；引擎侧全仓无 `LANGCHAIN_*`/`LANGSMITH_*` 清理代码 |
| 未实测 | 真实外发到 `api.smith.langchain.com` 的端到端（探针刻意只打到 127.0.0.1）；用户机命中该 env 的比例 |
| 推断 | `langgraph` 的每次节点执行都走 langchain-core 的 run-tree 回调，故阶段**产出**（含 `paper_md`，其中有题面截片段）同属可上报载荷 |

**两条处置**（都做，且分工明确）：
- **缓解（P1 就落，不等切换）**：引擎进程入口无条件剥离 `LANGCHAIN_*`/`LANGSMITH_*` env 并加守护测试。这是"摘除依赖之前先把门关上"，属独立缺陷修复，不依赖本重构成功。
- **根治（P7 后按构造成立）**：不再 import langsmith/langchain-core，暴露面归零；并新增守护"引擎生产代码零 lang* import"（§7.4）。

## 4. 自研内核设计

### 4.1 模块布局（新增，P1 全为增量文件）

```
engine/orchestrator/kernel/
  __init__.py          导出 GraphSpec / Graph / RunState / Interrupt / Resume / Snapshot
  spec.py              声明式图定义：节点表 + 静态边 + 条件边；build 期校验（未知节点、孤立节点、空路由）
  channels.py          通道存取：TypedDict 键集 + last-write-wins 合并（S3）；JSON 可序列化约束校验
  runtime.py           Graph.ainvoke(input, config)：superstep 循环、S2 入口路由、S4 串行、S8 END 后重入
  interrupt.py         Interrupt 控制流异常 + Resume 载体；节点重放语义（S5/S6）
  threads.py           ThreadStore：thread_id → 通道快照 + pending interrupt（替代 InMemorySaver，S7）
  introspect.py        get_graph().nodes / get_state(cfg).next / .tasks（S9 同形，使既有断言零改动）
  trace.py             执行轨迹记录器：节点进入/退出、通道增量、interrupt、resume 值（双轨比对的数据源）
```

设计约束（刻意的"小"）：
- **不做**并行超步、子图、map-reduce、streaming、reducer 注册表、消息历史语义——引擎只用到单链 + 一个带预算的循环图，超出需求即冗余。
- 通道值必须 JSON 可序列化（`graph.py:90-97` 的既有约定；红线：Key/句柄不入 State，见 `solve_loop.py:9-10`）；build 期与写入期各校验一次，违反即 `TypeError`（fail-loud，不静默丢字段）。
- 全部同步落库语义不变：业务检查点仍由 `SQLiteCheckpointStore` 经 `_persist_current/_persist_gate_passed` 写（`graph.py:398-416`），内核**不碰磁盘**，只管内存通道（保持 I4 的两层分工）。

### 4.2 与 LangGraph 的语义对照与偏离登记

| 语义 | LangGraph 行为 | 内核行为 | 偏离 | 理由 |
|---|---|---|---|---|
| S5/S6 节点重放 | 被中断节点从头重放 | 同 | 无 | 现 gate 节点首句即 `interrupt()`，等价；显式规定以防后续加语句时语义漂移 |
| 同节点多 `interrupt()` | 按序逐个消费 resume | **抛 `SpecError`（每节点至多 1 个挂起点）** | 有 | 现图只有 1 个；支持多挂起点要引入 resume-index 账本，属未需求复杂度。build 期静态检查发现第 2 个即报错，不会静默错 |
| 并行超步/fan-out | 支持，同超步多节点并发、通道冲突需 reducer | 不支持（静态检出 fan-out 即 `SpecError`） | 有 | 现图与内循环都是单链/带回边；出现 fan-out 时**必须显式改设计**而非静默降级 |
| 节点名 `:` 限制 | 存在（`graph.py:182` 注释） | 无 | 无影响 | 节点名继续沿用 `gate_{stage}`（S11 已进 RPC 事件字段） |
| `thread_id` 缺失 | 抛 `ValueError` | 同（消息文本不同） | 有（消息文本） | 该异常不外露（`ipc` 层不透这条路径），已核：`methods.py` 恒用 task_id |
| 通道 update 含未声明键 | 忽略/告警 | `KeyError` fail-loud | 有 | 与本项目 fail-loud 纪律一致；静默忽略正是"字段漂移"的来源 |

### 4.3 选择器与开关（过渡期唯一新增的运行时分支）

```python
# engine/orchestrator/impl.py
IMPLEMENTATION = os.environ.get("ERDOS_ORCH_IMPL", "langgraph")  # langgraph | native | shadow
```

- `langgraph`（P1~P5 默认）：走 `graph.py` 现实现，**行为与 HEAD 零差异**——这是"任意阶段可回滚"的实现方式。
- `native`：走内核；`graph.py` 的对外类与方法签名不变（只换内部 `_graph`）。
- `shadow`：**主跑 langgraph 并以其结果对外**；内核在同一份输入上影子跑，轨迹不一致 → ERROR 日志 + `shadow_divergence` 计数，**不改变对外行为**（灰度期宁可错在旧路，不可错在新路）。
- 沙箱/留痕/检查点写入**只在主实例发生**：shadow 实例注入 `RecordingStore`（只记不写），避免双写库、双花 token。
- P7 摘除依赖时，`impl.py` 与 `RecordingStore`、影子分支**整体删除**（不留兼容 shim）。

## 6. 双轨校验机制（过渡期并行运行两套实现）

### 6.1 为什么要双轨

本项目历史缺陷形状是"文档标 ✅、代码零调用方"与"单侧测试全绿、两侧一起跑才暴露"（10-09 的 `paused` 空转到超时即跨面回归）。自研内核的风险同类：**框架行为差异不会让代码报错，只会让编排"看起来跑通了但推进语义不同"**。所以比对必须是机器判定、进门禁、且自身可被测坏。

### 6.2 T1 — 单测级 parity 矩阵（每 PR 门）

一个 `ParityProbe` 把两套实现同时装配（同一 `StageRunner` 桩、同一脚本化 LLM、同一 recording sandbox），对下列 5 个序列做逐元素比对，任一不同即失败并打印**第一个分歧点**：

1. 动作序列：`run_current_stage` / `answer_gate` 返回的 `{"action","stage"}` 逐条；
2. 通道快照：每步后的 `{stage_index, results.keys(), gate_decision}`；
3. interrupt 载荷：`{"stage","message"}` 与挂起节点名（`.next`）；
4. 检查点写记录：`(task_id, stage, status, step, data)` 五元组序列（含 reject 时的 `delete_stage`）；
5. 异常：类型 + 消息（阶段跳级、非法 decision、无挂起门禁的过期应答）。

分支覆盖矩阵（每格一条用例，共 6×2）：正常四阶段 / 硬检查驳回重跑 / 人工 reject 重跑 / 门禁未决崩溃恢复 / 骨架模式（默认 runner）/ 最后阶段 complete。

### 6.3 T2 — 回归级双轨（批次门）

`scripts/run_regression.py --parity`：FakeLLM 20 题 + `run_paper_e2e.py` 4 题×4 阶段，两套实现各跑一遍，比对**RPC 事件流**（`stage.progress`/`artifact.ready`/`gate.failed` 序列与负载）、**留痕行数与四类事件分布**、**产物 sha256**、**检查点终态**、**墙钟分位**。按 DEC-024 口径，此通道不计入 SP1-7 ≥85% 判定分母。

### 6.4 T3 — 灰度双路（上线门）与"为什么不做生产逐请求镜像"

**不做逐请求镜像的三条硬理由**：① BYOK 下影子跑要**花用户两份 token**（评委/阶段各一次），违反预算红线；② `solving` 的影子跑要么真执行沙箱（双份时间、且代码可能改工作目录文件），要么依赖 `OperationLog` 复用——而复用会让轨迹必然不同，比对失去意义；③ 真实厂商非确定性（同 prompt 不同 tool_calls）会产出大量假阳性分歧，噪声淹没真问题。

**因此**：`shadow` 值只在**离线/开发机/FakeLLM 或已录制响应回放**时启用；生产灰度用**分组对照**（同版本两值），比对聚合结果而非逐请求。分歧若出现在分组聚合层 → 回退到 T1/T2 复现（分歧必可由 FakeLLM 通道复现，否则视为"真实厂商非确定性"单独分析，不算 parity 失败）。

**已核验的镜像成本口径**：`StageOrchestrator._runner` 是唯一外部副作用出口（`graph.py:143`），shadow 实例注入 `NullRunner`（返回主实例已产出的 data 副本）即可在不烧 token 的前提下比对**编排决策**（S2~S8）；但 `solving` 内循环的**工具分发决策**在 `pipeline._solving_tool_loop` 之下，NullRunner 模式下拿不到真产物 → 内循环 parity 只能在 T1/T2 做。**这是本方案已知的覆盖边界，写进验证报告而不是含混过去。**
