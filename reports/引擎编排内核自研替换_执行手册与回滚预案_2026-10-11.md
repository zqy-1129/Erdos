## 1. 一分钟版：现在系统是什么样

- `ERDOS_ORCH_IMPL` 不设 → **native（自研内核）**。四阶段编排、门禁挂起/恢复、求解内循环全部由 `engine/orchestrator/kernel/` 执行。
- 设 `ERDOS_ORCH_IMPL=langgraph` → 立刻回到旧实现。**改环境变量即可，不需要发版**；两套后端读写同一张 `checkpoints` 表，回滚不带数据迁移。
- 对外契约零变化：`contracts/engine-rpc.schema.json`（10 方法 / 6 事件 / transport）在本内核替换批次**一行未改**；客户端、服务端**零代码改动**。
  （指针：同日晚间的一致性审计批次给契约加了 `handshake.protocol_version` 与 `transport.limits.enforcement_status` 两处——那是握手版本单源与 G25 的落点，**与编排内核替换无关**，见《引擎侧文档一致性与口径对齐》§4.1。读"契约零 diff"时按批次区分，别当成同一件事。）
- 冷启动实测 p95 由 969.0ms 降到 **406.0ms**（12 样本）。
- 已知红线暴露已闭合：引擎在包导入期无条件剥离 `LANGCHAIN_*` / `LANGSMITH_*`（题面外泄通道，见设计文档 §2.3）。

## 4. 回滚预案

回滚分三层，成本从低到高。**默认值已翻转，所以第 1 层就是生产可用的回滚。**

| 层级 | 触发信号 | 操作 | 生效耗时 | 是否需发版 | 是否需数据迁移动作 |
|---|---|---|---|---|---|
| **L1 环境变量** | 灰度期编排异常（阶段不推进 / 门禁语义不对 / 恢复定位错） | 在拉起引擎前设 `ERDOS_ORCH_IMPL=langgraph`（用户环境或主进程 env） | 下一次引擎进程启动即生效（实测冷启动 ~0.9s） | 否 | **不需要**——两后端同一张 `checkpoints`/`operations` 表，兼容性由 `test_persistence_compat.py` 16 格 writer×reader×崩溃点矩阵证明 |
| **L2 单提交 revert** | 需要连代码一起退（如内核 bug 需要时间修） | `git revert <要退的提交>`；从新到旧依次可退，P5→P4→P3→P2→P1 各自独立 | 一次构建周期 | 是 | 不需要 |
| **L3 摘依赖后回退** | P7 之后才可能用到 | `git revert <P7 提交>` + `uv pip install -p .venv/Scripts/python.exe -e "./engine[dev]"`（恢复 46 包闭包） | 分钟级（含安装） | 是 | 不需要（表格式未变） |

判定门槛（不要凭感觉回滚）：

| 信号 | 门槛 | 动作 |
|---|---|---|
| 离线双轨分歧 | T1/T2 任一场景出现首个分歧 | **停止推进**，revert 当阶段提交；分歧用例进修复清单。不带病进下一阶段 |
| 灰度分组成功率 | 同批 n≥5 且 native 组比 langgraph 组低 ≥1 题 | L1 回滚 |
| 恢复定位错误（重放已完成阶段 / 跳级 / 门禁未决却推进） | 任一 `test_persistence_compat` 或 kill 演练用例红 | **立即 L1 回滚**（数据正确性优先，最高级） |
| 性能劣化 | 冷启动 p95 > 2000ms 或阶段墙钟破 `STAGE_TARGET_MS` | 不自动回滚，先归因；若归因到内核再退 P5 |
| 真实厂商非确定性导致的分组差异 | T1/T2 全绿但灰度聚合有差 | **不算 parity 失败**，按厂商行为差异单独立项 |

已执行的回滚演练（双向）：


## 7. 双轨校验的已知覆盖边界（坦白项）

1. **生产链路不做逐请求镜像**。原因：BYOK 下影子跑 = 让用户多付一份 token、多跑一遍沙箱，违反预算红线；且真实厂商非确定性会产出大量假阳性分歧。因此 `shadow` 这一档**没有实现**，双轨只在离线/回放通道成立（T1 单测、T2 回归）。
2. **T2 只覆盖 FakeLLM 通道**。真实 Key 下的工具调用顺序、评委判定差异不在双轨范围内（`--parity` 带 `--api-key` 或 `--gate rubric` 会直接拒启）。真实通道的对照方式是灰度分组比结果（§4），这比逐请求镜像弱，是明知并接受的取舍。
3. **真实厂商评委行为未实测**（量纲漂移、JSON 外裹 markdown、评分方差）——这条不是本批引入的，是 10-09 S6 批次遗留的既有边界，仍按 11-14 前真实回归观察。
4. **求解内循环的"工具分发决策"只能在离线通道比对**：主实例的 shadow 拿不到真产物（`NullRunner` 模式下 `solving` 产出为空），所以内循环一致性依赖 T1/T2，而非生产镜像。
5. **"回滚不需要数据迁移"的完整证据只有单测级**（`test_persistence_compat.py` 的 16 格 writer×reader×done_stages 矩阵）。**跨后端的进程级演练从未跑过**：A 后端跑到 solving → 换 B 后端续跑同一 `engine_home`。`run_regression --parity` 是"同一份输入、两个实现各自跑一遍"，不是"接力跑"。灰度期 L1 回滚实际会走接力路径，这是当前判据覆盖不到的地方（W32 灰度前应补一条接力用例）。
6. **parity 断言 `errors` 只比类型与消息、不比 usage 数字**，所以"用量采集是否满足契约"完全不在双轨网内。实证：W39 翻转默认装配后才发现真实厂商流式恒走本地估算（适配器从未索取 usage），而 T1/T2 当时**全绿**——双轨保证的是"两个实现一致"，不是"实现满足契约"。这条差别必须写清，否则双轨绿灯会被读成质量结论。
