# 引擎 stdio 编码与沙箱执行体修复（2026-10-08）

> 类型：缺陷修复交付快照（活文档口径不在此维护，本文件落盘后不改写）
> 关联：《任务执行手册》W2/W10 验收、《边界情况与异常处理规范》EC-T6/EC-S3/EC-D5、10-24 J-1024 三进程汇合门
> 环境：Windows 11 26200 / Python 3.12.15（uv 管理，`.venv` 零依赖安装 `-e ./engine[dev]`）/ develop @ d3eefc9

## 1. 现象

1. `pytest` 全量跑在本机有 4 例红灯（Linux CI 全绿）：`test_key_without_model_config_rejected`、`test_missing_home_rejected`、`test_startup_corrupt_store_fails_closed`（UnicodeDecodeError）、`test_run_paper_e2e_script_no_key_smoke`（stdout 为 None）。
2. 客户端 10-08 壳级冒烟记录：FakeLLM 无 Key 模式下 **solving 阶段耗时约 120s**，正好命中沙箱单次执行上限；analysis/modeling/writing 均毫秒级。

## 2. 根因

| # | 根因 | 证据 |
|-|-|-|
| R1 | 引擎三管道未固定编码。Windows 控制台默认码页常为 cp936/GBK，`EventEmitter` 与 `encode_error` 用 `ensure_ascii=False` 写中文，落管道即 GBK 字节；而主进程（`client/main/engine-host/rpc.ts` 按 Buffer/utf8 解析）与测试（`encoding="utf-8"`）都按 UTF-8 读 → 乱码/解码失败/事件被静默丢弃 | `engine/ipc/events.py:60`、`engine/ipc/rpc.py:68-72`、`engine/tests/test_entry_wiring.py:51` |
| R2 | 驱动脚本 `run_paper_e2e.py` / `run_regression.py` 同样继承宿主码页输出中文进度 | 失败用例 `test_run_paper_e2e_script_no_key_smoke` |
| R3 | 沙箱执行体写死裸 `"python"`（`subprocess_sandbox.py:65`）。本机 bash 里 `python -c` 直接返回"Python was not found"（微软商店 App Execution Alias 占位 stub），GUI 派生场景该 stub 不产出即挂到执行超时上限；PyInstaller 冻结后 `sys.executable` 又是引擎自身 exe，写死任何单一值都不成立 | `python -c "print('ok')"` 退出码 49；`engine/sandbox/subprocess_sandbox.py:65` |
| R4 | 测试污染：pytest-cov 经 `COV_CORE_SOURCE` 把覆盖率钩子下发给引擎子进程，coverage 导入期告警（含 Windows 中文错误串，按 GBK 写出）在 `configure_stdio()` 之前落进协议管道 | 失败 traceback 的 input buffer 头：`coverage/core.py:108: CoverageWarning: Couldn't import C tracer: DLL load failed…`（本机应用控制策略禁用 C tracer 才触发）；`.venv/Lib/site-packages/a1_coverage.pth`、`pytest-cov.pth` |

R1 与 R3 是产品缺陷（Windows 是 P0 目标平台，且直接决定 10-24 汇合门能否通过）；R4 只影响测试环境，但会让"进程级测试"在带覆盖率的正式验收跑里假红。

## 3. 修复

- **R1**：新增 `engine/ipc/stdio.py::configure_stdio()`，进程入口强制 stdin/stdout/stderr 为 UTF-8，stdout 行结束符固定 LF；`engine/__main__.py:main()` 首行调用（早于任何 stdio 读写与 `_fail` 诊断）。跨端条款登记进 `client/main/engine-protocol.md` §2（编码基线：UTF-8 + LF，主进程无需设置码页，也不得依赖 `PYTHONIOENCODING`）。
- **R2**：两个驱动脚本 `main()` 同样调用 `configure_stdio()`。
- **R3**：新增 `resolve_python()` + `_probe_interpreter()`，解析链为 `ERDOS_SANDBOX_PYTHON`（打包分发时由壳指向随附解释器）→ 未冻结时 `sys.executable` → PATH 上 `python3`/`python`（逐个 `-c pass` 探测，5s 上限）；显式配置只认它，探测失败**不静默回退**。执行体不可用时快速返回结构化错误（模型可读 + 给出下一步动作），不再烧掉 120s 执行预算。`SubprocessSandbox` 增 `python=` 参数并缓存探测结果。
- **R4**：`test_entry_wiring._child_env()` 剥离 `COV_CORE_*` / `COVERAGE_PROCESS_*` / `PYTHONSTARTUP`，进程级测试不再继承覆盖率钩子。

## 5. 遗留与后续

1. **打包分发口径**：冻结版必须由壳设置 `ERDOS_SANDBOX_PYTHON` 指向随附解释器，或走 Docker（DEC-006 正式隔离路径）。该条款需在 W17/W18 落地时同步进 engine-protocol 与打包脚本，本轮只在 `resolve_python()` docstring 与代码路径中生效。
2. **subprocess 模式内存上限未实施**：`memory_limit_mb` 仍只是记录（Windows Job Object 待接入），与 PRD 6.1"内存 ≤2GB"存在口径差，属已知缺口，不属本轮范围。
3. **FakeLLM solving 120s 的实测复核**应在 10-24 J-1024 联调时用壳级冒烟复跑确认（本轮为引擎侧直接证据）。
4. 本机 `python` 是商店 stub 且应用控制策略禁用 coverage C tracer——任何在本机跑验收的人都需要 `.venv` 显式解释器，别假设 `python` 可用。
