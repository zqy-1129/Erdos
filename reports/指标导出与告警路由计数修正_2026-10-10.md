# 运行期计数接上 /metrics 与告警路由漏计修正（2026-10-10）

## 1. 结论先行

1. **两处"有计数、无消费方"接上了 Prometheus**：`AlertRouter.routed_counts`（10-09 批）与 `MessageBus.delivery_failures`（10-10 早批）此前只有测试读取——这正是本项目反复出现的"能力已实现、零调用方"模式，计数存在但没人看等于没有。现在导出为 `erdos_alert_routed_total{channel}` 与 `erdos_bus_delivery_failures_total{topic}`。
2. **测试先红，抓出一个真缺陷**：`BrokerAlertOutlet.emit` 的非去重分支走的是 `AlertRouter.channel_for`（纯映射、**不计数**），而采样告警一律 `dedupe=False`——也就是**最繁忙的告警来源在 `routed_counts` 里永远是 0**。日志明明写着 `channel=message`，计数全 0。新增 `AlertRouter.note()` 让两条路径都计数。
3. **指标是镜像，不是第二份账本**：真源仍在各自对象里，Gauge 只在抓取时导出，避免两处记账对不上。
4. **零契约 diff**：`/metrics` 是 `include_in_schema=False` 的运维端点，不在 openapi 里——冻结日不动契约（contract_audit 四项仍 `[OK]`，60 路径×方法未变）。
5. 状态：**已实现待验收**（Prometheus 侧的告警规则不在仓库内，见 §5 #1）。

## 2. 为什么刷在抓取时，而不是采样循环里

采样循环受 `monitoring_enabled` 控制，可以整条关掉；而"告警路由了几条、总线消费者炸了几次"与监测开关无关。**把导出挂在循环上，等于让关掉监测顺带关掉告警可观测性**——这两件事没有因果关系，不该绑在一起。

代价是抓取路径多两次字典遍历（有界：通道 3 个、主题为已注册主题数），换来的是与监测解耦。取属性一律 `getattr` 兜底：`/metrics` 可能在 lifespan 装配完成前被抓到，那时返回 500 比少两条指标糟糕得多。

## 3. 缺陷取证（值得记的一条）

| 步骤 | 观察 |
|-|-|
| 新写的 API 级用例断言 `erdos_alert_routed_total{channel="message"} 1.0` | 红：响应里三条通道全是 `0.0` |
| 看被测那次 emit 的日志 | `业务告警外发：level=P2 channel=message ...` ——**路由确实发生了** |
| 直接调 `outlet.routed_counts` | `{FEISHU: 0, EMAIL: 0, MESSAGE: 0}` |
| 读 `emit` 分支 | `if triggered and dedupe: router.route(...)`（计数）／`else: AlertRouter.channel_for(...)`（纯映射，不计数） |
| 对照调用方 | `infra/sampling.py` 的采样告警一律 `dedupe=False`（10-09 批刻意如此，避免静默窗口吞掉"触发→恢复→再触发"）→ **主路径全部漏计** |

这类缺陷的特点：**指标不是不存在，而是永远为 0**，看上去像"系统很健康"。比没有指标更坏，因为它会误导值班与容量判断。修法是把"记一次路由"独立成 `note()`，`route()`（含去重）复用它，非去重分支直接调它；并补回归用例 `test_dedupe_false_path_is_still_counted` 钉住。
